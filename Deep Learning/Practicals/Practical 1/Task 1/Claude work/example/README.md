# Building a CSV data visualizer

The goal of this exercise is to build a simple HTML artifact that lets you load a CSV file and visualize its data clearly: table, statistical summaries and bar chart. Everything runs in the browser, without any server.

## Development philosophy: specifications + AI

This exercise has been designed to show a **structured development method** where specifications precede code. The idea is not that an AI "writes the code for you", but that **you design and specify the solution and the AI implements it**.

### Why specify before programming?

Writing code without knowing exactly what has to be built is the main cause of runaway projects, disorganized code and features that do not match what was needed.

This exercise follows a protocol of **three reference documents** that avoid this problem:

1. **`spec.md` — What the system must do.**
   Describes the functional requirements: what the user must be able to do, which messages must be shown, what format the data must have. It does not talk about code, files or libraries. Only about the **expected behavior**.
   
   > *Ask yourself: if no programmer existed (neither human nor AI), what should this program do?*

2. **`architecture.md` — How the project is organized.**
   Defines the file structure, the responsibility of each file, the libraries used and the design decisions. It is the **blueprint** of the project.
   
   > *Ask yourself: how many files do I need? What does each one do? Which library makes the work easier?*

3. **`tasks.md` — What needs to be done, in what order.**
   Turns the specification into a list of small tasks ordered by phases. Each task is **independent and verifiable**.
   
   > *Ask yourself: into what small steps can I split this problem?*

There is an additional document, **`reglesIA.md`**, which defines a way of working that ensures developers keep responsibility over the systems they build, even when most of the implementation is generated by AI.

### What does this method give you?

| Without specifications          | With specifications                          |
| ------------------------------- | -------------------------------------------- |
| You start programming blindly   | You know exactly what you have to build      |
| The AI invents the architecture | You control the project architecture         |
| The code quickly runs out of control | Each task is small and verifiable       |
| You don't know if you are done  | The acceptance criteria mark when it is done |
| You don't get structured code   | You get organized and commented code         |

### How a person interacts with the AI assistant

This method is designed so that the person **does not copy and paste code**, but **dialogues with the AI** to build the solution step by step. Here is how it works:

**1. The person writes the specifications.**
   You begin by writing the three specification files:

- `spec.md` → explains what the program must do.

- `architecture.md` → explains how many files are needed and what each one does.

- `tasks.md` → breaks the work down into small tasks.
  
  > *This is the most important step. If you don't know how to write these files, review the concepts before continuing.*

**2. The person asks the AI for code, task by task.**
   Instead of saying "do the whole project for me", you ask for **one task at a time**:

    > Read spec.md, architecture.md and tasks.md and start
    implementing the first task.

**3. The person verifies the task**

  If there is any error, ask the AI to fix it.

**4. The person repeats the process for each task.**
   Once the previous task is done and verified, ask for the next one:

    > Now implement the next task

**What must be done in each interaction:**

| Step | Action                                                          |
| ---- | --------------------------------------------------------------- |
| 1    | Write and review the `.md` files before asking for code         |
| 2    | Ask for **one task at a time**, not all of them together        |
| 3    | Review and test the code the AI returns (do not accept blindly) |
| 4    | Inform the AI of any error or unexpected behavior               |
| 5    | Ask for the next task or finish.                                |

**What must NOT be done:**

- **Do not ask "do the whole project for me at once".** This generates disorganized code that does not follow the specifications.
- **Do not accept code without reading it.** If you don't understand a line, ask the AI why it works that way.
- **Do not skip tasks.** Each task depends on the previous one. Skipping one can cause errors in future tasks.
- **Do not ignore errors.** If something does not work, report it and ask for a fix.

**Examples of prompts you can use:**

```
# To start a task:
"Read spec.md, architecture.md and tasks.md. Implement task [task ID]."

# To ask for an explanation of the code:
"Explain step by step what the function [function name] does."

# To fix an error:
"The chart is not showing. Review app.js and tell me what is wrong."

# To add an unplanned improvement:
"I want to add [description of the improvement]. Is it consistent with the current architecture? If it is, tell me which new task should be created in tasks.md."

# To verify that everything works:
"Review all the project files and tell me whether the code is consistent with the specifications in spec.md and architecture.md."
```

**Why is it important to interact task by task?**

- Each task is **small and verifiable**: it is easier to detect errors.
- The AI can **follow the specifications precisely**: it does not skip steps or invent things.
- The person **learns in the process**: by reading the code of each task, they understand how everything fits together.
- If something fails, you **know exactly where to look**: if task T3.2 fails, the problem is in the data table, not in the chart.

### Why is it important to control the specifications?

- **If you don't control `spec.md`**, the AI may implement features you don't need and forget the ones you do.
- **If you don't control `architecture.md`**, the AI may invent a complicated structure you don't understand.
- **If you don't control `tasks.md`**, the AI may skip steps or implement them in the wrong order.

**You want to control the project.** And that starts with being able to explain what you want. And that is precisely what this method teaches you: how to break down a problem, define it precisely and verify that the solution matches what you were asking for.

## Do you need to understand the code the AI generates?

One of the most important ideas when working with AI to program is avoiding **cognitive debt**.

When we use code agents (such as ChatGPT, Claude or other assistants), it is very easy to let the AI implement increasingly large changes to the point where **the code stops being truly ours**. It works, but we no longer understand why it works. At that moment we start to accumulate cognitive debt: the distance between what the program does and what we understand of it grows larger and larger.

In the short term this seems efficient, but in the medium term it becomes a problem. If an error appears, if the system needs to be modified or a new feature added, we no longer have the concepts needed to make decisions or even to write a good specification for the AI. We limit ourselves to asking the AI for poorly specified changes, accumulating even more debt.

The goal, therefore, **is not to write all the code manually**, but to keep a **level of understanding** sufficient to continue **actively participating** in the development. Every time the AI generates a solution, we should be able to explain:

- why it works,
- which design decisions were made,
- which alternatives there were,
- and what limitations it has.

Only in this way can we keep control of the project.



This is one of the great challenges of AI-assisted programming: **delegating repetitive work without delegating understanding**. The AI can write a lot of code, but the responsibility to understand it remains ours. In short, the goal is not to produce more lines of code, but to preserve the ability to think about the system we are building.
